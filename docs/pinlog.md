## 피드 후보 조회가 느렸던 이유

상위 100건을 가져오는 쿼리가 활성 발행 컬렉션 약 66만 건을 정렬하고 있었습니다. 실행 계획을 확인하니 `ORDER BY COALESCE(published_at, created_at)`이 기존 인덱스의 정렬 순서와 맞지 않았습니다.

정렬 기준을 `published_at DESC, id DESC`로 변경했습니다. 조건에 맞는 발행 컬렉션은 DB CHECK 제약으로 `published_at`이 NULL일 수 없으므로, 이 범위에서 COALESCE를 제거해도 결과는 같았습니다. 추천 점수나 정책을 변경하지 않고 인덱스를 활용하도록 수정했습니다.

## 측정 조건과 결과

아래는 실제 사용자 트래픽이 아닌 **합성 데이터 벤치마크** 결과입니다. 상세 실행 계획과 명령은 [PR #183](https://github.com/Team-PinLog/back/pull/183)에 남겼습니다.

| 구분 | 조건 / 결과 |
| --- | --- |
| 데이터 규모 | Record 천만 건 규모, Collection 약 66.8만 건 |
| DB 자원 | 벤치마크용 1 CPU·1GiB 제한 |
| 쿼리 측정 | 콜드 재기동 후 같은 실행 안에서 변경 전후 비교 |
| 피드 후보 쿼리 | 236.648 → 2.295ms |
| API 측정 | 동일 데이터·자원 제한, Record 2만 건을 가진 회원, 워밍 3회 후 10회 측정 |
| 피드 API 중앙값 | 368 → 197ms |

쿼리 실행 시간과 API 전체 응답 시간은 서로 다른 측정입니다. 쿼리 개선 배율을 API 전체의 개선 배율로 표현하지 않습니다.

## 검증과 남은 한계

실행 계획 기반 회귀 테스트를 추가하고, 기존 정렬식으로 되돌렸을 때 테스트가 실패하는지 확인했습니다. 테스트 DB는 데이터가 적어 순차 스캔이 더 저렴할 수 있으므로, 인덱스 경로를 확인할 수 있도록 테스트 조건을 지정하고 정렬 계획을 검증했습니다. 이 테스트와 대량 데이터 성능 측정은 목적을 구분했습니다.

해당 PR 시점에는 API에 남은 Keyword 조회 병목도 확인했습니다. 벤치마크 생성기가 AI 파생 데이터를 함께 생성하지 않으므로, 이 결과만으로 전체 검색·추천 성능을 검증했다고 보지는 않습니다.

## 이 작업에서 배운 점

인덱스가 존재하는 것과 쿼리가 그 인덱스를 활용하는 것은 다릅니다. 정렬식을 바꾸기 전에는 데이터 제약과 결과 동일성을 확인하고, 변경 후에는 쿼리와 API를 각각 측정해야 개선 범위를 설명할 수 있었습니다.
